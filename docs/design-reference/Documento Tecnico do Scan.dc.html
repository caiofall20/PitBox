Pitbox — reconhecimento de miniaturas no scan

Documento técnico · versão 1 · outubro de 2026

1. Objetivo e premissas

O scan identifica uma miniatura a partir de uma foto, preenche o cadastro e verifica se o usuário já tem o modelo. A solução segue três premissas:

  • Sem serviços pagos e sem cota de uso: todos os modelos são abertos e rodam em infraestrutura própria ou no aparelho do usuário.
  • Banco de dados PostgreSQL, com as extensões pgvector e pg_trgm.
  • Nenhum treinamento é necessário para começar. A precisão cresce com as fotos aprovadas pela moderação.

2. Fluxo do scan

Cada etapa só roda se a anterior não tiver resolvido a identificação com confiança suficiente.

  1. Código de barras. Se a foto mostra a cartela, o código é lido e buscado em catalogo_modelos.codigo_barras. Encontrou: confiança 100%.
  2. Recorte. O fundo é removido para que a comparação considere só o carrinho.
  3. Embedding da imagem. Um modelo de visão converte a foto em um vetor de 384 números.
  4. Busca por similaridade. O vetor é comparado com as fotos aprovadas do catálogo (identificação) e com os itens do próprio usuário (duplicata).
  5. Leitura de texto. O OCR lê nome e série impressos na cartela e reforça ou corrige o resultado da imagem.
  6. Pontuação. Os sinais viram uma confiança por campo, exibida na tela de revisão.

4. Modelo de dados

create extension if not exists vector;
create extension if not exists pg_trgm;

create type perfil as enum ('colecionador','moderador','admin');

create table usuarios (
  id uuid primary key default gen_random_uuid(),
  nome text not null, email text unique not null,
  perfil perfil not null default 'colecionador',
  ativo boolean not null default true,
  criado_em timestamptz not null default now()
);

create table catalogo_modelos (
  id uuid primary key default gen_random_uuid(),
  marca text not null, modelo text not null, ano int,
  serie text, escala text, codigo_barras text unique,
  status text not null default 'pendente',     -- pendente | aprovado
  enviado_por uuid references usuarios(id)
);

create table catalogo_fotos (
  id uuid primary key default gen_random_uuid(),
  modelo_id uuid not null references catalogo_modelos(id),
  url text not null, embedding vector(384) not null,
  status text not null default 'pendente',     -- pendente | aprovada | rejeitada
  enviada_por uuid references usuarios(id),
  revisada_por uuid references usuarios(id)
);

create table itens (
  id uuid primary key default gen_random_uuid(),
  usuario_id uuid not null references usuarios(id),
  modelo_id uuid references catalogo_modelos(id),
  numero int not null, preco_pago numeric(10,2),
  foto_url text, embedding vector(384),
  criado_em timestamptz not null default now()
);

create table desejos (
  usuario_id uuid references usuarios(id),
  modelo_id uuid references catalogo_modelos(id),
  primary key (usuario_id, modelo_id)
);

create index on catalogo_fotos using hnsw (embedding vector_cosine_ops);
create index on itens using hnsw (embedding vector_cosine_ops);
create index on catalogo_modelos using gin (modelo gin_trgm_ops);

Código 1. Esquema mínimo. Fotos ficam no sistema de arquivos do servidor ou em um bucket compatível com S3; o banco guarda só a URL.

5. Consultas do scan

Identificação no catálogo, usando apenas fotos aprovadas:

select m.id, m.marca, m.modelo, m.ano, m.serie, m.escala,
       1 - (f.embedding <=> $1) as similaridade
from catalogo_fotos f
join catalogo_modelos m on m.id = f.modelo_id
where f.status = 'aprovada'
order by f.embedding <=> $1
limit 5;

Verificação de duplicata na coleção do usuário. Se o modelo já foi identificado, a comparação por modelo_id basta; a busca por vetor cobre itens cadastrados sem vínculo com o catálogo:

select id, numero, 1 - (embedding <=> $1) as similaridade
from itens
where usuario_id = $2
  and (modelo_id = $3 or embedding <=> $1 < 0.15)
order by embedding <=> $1
limit 3;

Reforço pelo texto lido na cartela:

select id, modelo, similarity(modelo, $1) as sim_texto
from catalogo_modelos
where status = 'aprovado' and modelo % $1
order by sim_texto desc
limit 5;

6. Pontuação e confiança

Para cada candidato, a confiança combina os sinais disponíveis. Os pesos abaixo são o ponto de partida e devem ser calibrados com scans reais:

se código de barras encontrado:  confiança = 1.00
senão: confiança = 0.65 × sim_imagem + 0.35 × sim_texto
       (sem texto legível: confiança = sim_imagem)
ConfiançaNa tela de revisãoComportamento
≥ 90%Selo “Lido”Campo preenchido sem destaque
75–89%Selo amarelo “Confira”Campo preenchido e destacado
< 75%Sem sugestãoMostra os 3 candidatos mais próximos ou cadastro manual

O preço pago nunca é inferido; o campo sempre pede preenchimento manual.

As regras ficam no próprio banco com Row Level Security, para que nenhuma tela ou API consiga contorná-las:

alter table itens enable row level security;
create policy itens_do_dono on itens
  using (usuario_id = current_setting('app.usuario_id')::uuid);

alter table catalogo_fotos enable row level security;
create policy moderar_fotos on catalogo_fotos for update
  using (exists (select 1 from usuarios u
                 where u.id = current_setting('app.usuario_id')::uuid
                   and u.perfil in ('moderador','admin')));

8. Moderação e aprendizado contínuo

  1. O colecionador salva uma miniatura. Se o modelo não existe no catálogo, nasce um catalogo_modelos pendente; a foto vira um catalogo_fotos pendente.
  2. A fila de moderação mostra o envio com a sugestão mais parecida já aprovada. Acima de 90% de similaridade, o moderador vê o botão “Mesclar com existente”, que evita modelos duplicados com nomes diferentes.
  3. Fotos aprovadas passam a participar da busca imediatamente. Não há retreino: o índice vetorial é atualizado na inserção.
  4. Quando o usuário corrige um campo sugerido, a correção é registrada e entra na fila como sinal de qualidade daquela foto de referência.

Se depois de alguns milhares de fotos aprovadas a precisão ainda não for suficiente, é possível treinar uma camada de classificação sobre os embeddings do DINOv2, sem placa de vídeo dedicada.

9. Mobile

Fase 1 — PWA. O mesmo app web é instalável na tela inicial. A câmera é acessada pelo navegador, e código de barras, embedding e OCR podem rodar no próprio aparelho com WebAssembly ou WebGPU. Um único código atende Android, iOS e desktop.

Fase 2 — app nativo (opcional). Com Expo (React Native) e ONNX Runtime Mobile, o mesmo modelo roda mais rápido e funciona sem conexão. A interface da fase 1 serve de base.

10. Hospedagem sem custo de uso

  • PostgreSQL com pgvector em Docker, em servidor próprio ou em uma VM gratuita.
  • Com o embedding calculado no aparelho, o servidor só recebe o vetor e executa a busca, o que mantém a carga baixa.
  • Um serviço Python (FastAPI + ONNX Runtime) fica como alternativa para aparelhos sem desempenho suficiente.

11. Riscos e cuidados

  • Licenças. Evitar o YOLO da Ultralytics, que é AGPL e obrigaria a abrir o código do produto. Para detecção de objetos, usar RT-DETR (Apache 2.0).
  • Imagens de referência. Formar o catálogo com fotos dos próprios usuários. Coletar imagens de lojas ou sites pode violar os termos de uso deles.
  • Início lento. Com o catálogo vazio, o reconhecimento depende do OCR. Moderadores podem fotografar suas coleções para criar a base inicial.
  • LGPD. Fotos e e-mails são dados pessoais: registrar consentimento e apagar os dados quando a conta for excluída.
